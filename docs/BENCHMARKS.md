# 벤치마크 (명세 §7)

명세 §7의 측정 지침(TPS · p50/p99 지연 · 연결당 CPU/메모리/할당, 메시지 100B·1KB·64KB, 동시 접속 수)을 실행하는 하니스가
`benchmarks/`에 있습니다.

```bash
python -m benchmarks.bench                                        # 기본: 3 프로토콜 × 100B/1KB/64KB × 1/16/128 연결
python -m benchmarks.bench --sizes 100,1024 --concurrency 1,16 --duration 2 --json results.json
```

| 대상 | 설명 |
| :-- | :-- |
| `lcp` | 전체 스택: `LCPServer` / `LCPClient` (세션, 상관관계, 타임아웃, 백프레셔 포함) |
| `lcp-raw` | LCP 프레이밍만: `FrameDecoder` + 직접 만든 프레임 (세션 계층 없음). **HTTP와의 프로토콜 비교는 이 대상을 쓰세요** |
| `http1` | 최소 구현 asyncio HTTP/1.1 keep-alive 에코 서버/클라이언트 (JSON 본문, `Content-Length`) |

서버는 **별도 프로세스**로 실행되고(`benchmarks/servers.py`), 클라이언트는 연결당 요청 1개씩 보내는 폐쇄 루프입니다.
서버 프로세스가 측정 구간 앞뒤로 CPU 시간·GC 횟수·최대 RSS 스냅샷을 보고하므로 요청당 서버 CPU(µs)와 1000 요청당 GC 횟수
(파이썬에서 "할당 횟수"에 가장 가까운 지표)를 함께 얻습니다. 응답이 요청 본문과 다르면 즉시 실패합니다.

## 예시 결과 (참고용)

환경: Linux 샌드박스, **vCPU 1개**(클라이언트와 서버가 같은 코어를 공유), CPython 3.12.3, 연결 16개, 구간 2초.
절대값이 아니라 **상대 비교**로만 읽으세요.

| 프로토콜 | 크기 | TPS | p50 ms | p99 ms | 클라이언트 µs/op | 서버 µs/op |
| :-- | --: | --: | --: | --: | --: | --: |
| lcp | 100 B | 9,275 | 1.68 | 3.41 | 48.7 | 56.7 |
| lcp-raw | 100 B | 19,579 | 0.78 | 1.72 | 21.8 | 28.1 |
| http1 | 100 B | 31,554 | 0.47 | 1.14 | 12.3 | 18.7 |
| lcp | 1 KB | 9,516 | 1.65 | 3.21 | 48.2 | 55.1 |
| lcp-raw | 1 KB | 14,382 | 1.02 | 2.56 | 29.4 | 37.1 |
| http1 | 1 KB | 27,170 | 0.54 | 1.40 | 14.4 | 21.5 |
| lcp | 64 KB | 4,946 | 3.18 | 6.50 | 96.4 | 102.2 |

## 해석

- **순수 파이썬에서는 최소 HTTP/1.1이 더 빠릅니다.** 작은 메시지에서 `http1`은 `lcp-raw`의 약 1.6배, 전체 스택 `lcp`의 약 3.4배입니다.
  이유는 구현 언어에 있습니다. HTTP 헤더 파싱은 `StreamReader.readuntil`/`bytes.split` 같은 **C로 구현된** 연산이지만,
  LCP 프레이밍은 인터프리터에서 실행되는 파이썬 코드(헤더 `struct` 해석, 검증, TLV 디코드, 객체 생성)입니다. 이 저장소는 디코드
  경로를 최적화했지만(메타데이터 디코드 캐시, 신뢰 생성자) 언어 한계는 남습니다.
- **프로토콜 설계의 이점은 컴파일 언어에서 나타납니다.** 고정 오프셋 헤더와 길이 접두 필드는 텍스트 파싱·재할당이 필요 없어
  Go/Rust/C++ 구현에서 의미가 큽니다. 이 저장소는 **의미론의 기준 구현**이며, 포트를 만들 때 같은 하니스 개념과
  `tests/test_spec_conformance.py`의 골든 벡터를 재사용하는 것을 권장합니다.
- 페이로드가 커질수록(64 KB) 메모리 복사가 지배적이라 프로토콜 간 차이가 줄어듭니다(`lcp-raw` ≈ `http1`의 0.9배).
- `lcp`와 `lcp-raw`의 차이가 세션 계층의 비용(요청당 태스크·future·타임아웃·인증/라우팅 검사)입니다. 이것이 상관관계 멀티플렉싱,
  백프레셔, 인증 같은 기능의 대가입니다.

## 한계와 확장

- 명세가 비교 대상으로 든 **HTTP/2(gRPC/Protobuf)**와 **MQTT(QoS 1)**는 외부 패키지(grpcio, paho-mqtt)와 브로커가 필요해
  포함하지 않았습니다. `benchmarks/clients.py`에 `Conn` 프로토콜(`request`/`close`)을 구현한 클래스를 추가하고
  `benchmarks/servers.py`에 서버를 등록하면 같은 표에 나타납니다.
- 명세가 제시한 1,000 ~ 50,000 동시 접속은 단일 파이썬 프로세스·단일 코어로는 의미 있는 측정이 어렵습니다(`ulimit -n`,
  클라이언트 CPU 포화). 그 규모는 부하 생성기를 여러 프로세스/머신에 분산하는 환경에서 측정하세요.
- 같은 머신에서 클라이언트와 서버가 코어를 나누므로 지연 수치에 스케줄링 잡음이 섞입니다. 코어를 분리(`taskset`)하면 더 안정적입니다.
