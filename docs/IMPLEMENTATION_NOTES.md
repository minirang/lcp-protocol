# 구현 노트 — 명세 해석, 불일치, 결정 사항

이 문서는 LCP 명세 v1.3.0을 구현하면서 발견한 **모호하거나 서로 어긋나는 부분**과, 그에 대해 이 저장소가 내린 **결정**을
기록합니다. 명세를 개정할 때 그대로 참고할 수 있도록 "명세 문구 → 문제 → 이 구현의 처리" 형식으로 적었습니다.
각 결정은 테스트로 고정되어 있습니다(괄호 안은 대표 테스트).

## 1. 명세의 불일치 · 오류

| # | 명세 위치 | 문제 | 이 구현의 처리 |
| :-: | :-- | :-- | :-- |
| E1 | §3.2 표, Status Code 행 | "표 4.2 참조"라고 되어 있으나 상태 코드 표는 **§5.2**에 있음 | §5.2를 기준으로 구현. 문서 오타로 판단 |
| E2 | §1, §3 "4바이트 정렬(Alignment)을 완벽히 준수" | 정렬을 보장하는 규칙이 없음: TLV는 `3 + N` 바이트, 페이로드는 임의 길이이며 패딩 규정이 없음. §6 참조 프레이머도 `16 + meta_len + payload_len`으로 프레임 크기를 계산 | **패딩 없음**. 보장되는 것은 16바이트 헤더(각 필드가 자연 정렬)뿐. 패딩을 넣으면 참조 프레이머와 상호운용이 깨지므로 의도적으로 넣지 않음 (`test_no_padding_between_header_metadata_and_payload`) |
| E3 | §3.2 Version 행 "`BAD_REQUEST` 후 연결 종료" ↔ §6 `_abort` | 참조 코드는 응답을 보내지 않고 소켓만 닫음 | 헤더 위반(Version·Message Type·PING/PONG 길이·크기)에는 **오류 응답을 best-effort로 보낸 뒤 종료**. 오류 응답이 TCP RST로 유실되지 않도록 짧게 lingering close. Magic 불일치만 명세대로 **응답 없이** 종료 (`test_header_violations_get_bad_request_then_close`, `test_reply_survives_a_peer_that_keeps_streaming_the_oversized_body`) |
| E4 | §1 "버전 1.3.0"과 §3.2 Version `0x01` | 문서 버전과 와이어 버전이 별개인데 구분이 없음 | 와이어 `Version`은 `0x01`(`PROTOCOL_VERSION`), 문서 버전은 `SPEC_VERSION = "1.3.0"`. 패키지 버전(`0.1.0`)은 또 별개 |
| E5 | §5.2 | 상태 코드가 `0x00, 01, 02, 04, 08, 09, 0F`로 비어 있음(0x03, 0x05–0x07, 0x0A–0x0E 미정의) | 수신한 미정의 코드는 **정수 그대로 보존**하고 거부하지 않음(전방 호환). 이 구현은 미정의 코드를 송신하지 않음 (`test_decodes_back_to_back_frames_and_unknown_status`) |
| E6 | §3.2 Magic 행 | 참조 프레이머는 Magic을 16바이트가 모일 때까지 검사하지 않음 | 2바이트가 도착하는 즉시 검사해 HTTP 등 다른 프로토콜을 바로 차단. 16바이트 이상이 모인 입력에서는 참조 프레이머와 결과가 동일 (차분 테스트) |

## 2. 명세가 정하지 않은 사항에 대한 결정

| # | 주제 | 결정 |
| :-: | :-- | :-- |
| D1 | **바이트 순서** | 모든 다중 바이트 정수는 빅엔디안(참조 코드의 `">HBBBBHII"`). TLV `Length`도 빅엔디안 |
| D2 | **Correlation ID** | `uint32`. 이 구현은 `1`부터 순환 할당하고 `0`은 "상관 ID를 알 수 없는 오류 응답"(예: 연결 수 초과 `BUSY`)용으로 예약. 수신 측은 `0`도 거부하지 않음 |
| D3 | **PONG의 Correlation ID** | `PING`의 값을 그대로 echo (RTT 측정·`ping()` 매칭에 필요) |
| D4 | **상태 코드를 싣는 메시지** | `RES`와 `EVT_ACK`이 결과 상태를 가짐. 요청 쪽(`REQ`/`EVT`/`PING`/`PONG`)의 `Status`는 `OK(0)`으로 보내며 수신 시 무시 |
| D5 | **`REQ`의 `TARGET_PATH`** | 필수. 없거나 `/`로 시작하지 않거나 제어 문자가 있으면 `BAD_REQUEST`(연결 유지). 라우트가 없으면 `NOT_FOUND` |
| D6 | **`EVT` / `EVT_ACK` 의미** | 양방향(클라이언트→서버, 서버→클라이언트). `TARGET_PATH`는 이벤트 토픽(선택; 없으면 기본 핸들러). 수신 측은 핸들러 실행 후 같은 Correlation ID로 `EVT_ACK`을 보내며 핸들러 결과(상태)를 담음 |
| D7 | **이벤트 전달 보장** | MQTT QoS 1과 같은 *at-least-once*: ACK 타임아웃 시 **같은 ID**로 재전송 가능(`retries`). 수신 측은 연결 단위로 최근 `event_dedupe_window`(1024)개 ID와 결과를 기억해 핸들러 재실행을 막고, 처리 중인 중복은 무시. `BUSY` ACK은 "미처리"이므로 기억하지 않음 (`tests/test_events.py`) |
| D8 | **`AUTH_TOKEN` 전송 빈도** | `REQ`/`EVT`마다 검증(세션 캐시 없음, 만료 토큰이 연결에 남지 않도록). `PING`/`PONG`·`RES`/`EVT_ACK`에는 불필요. 연속 `max_auth_failures`(기본 3)회 실패하면 `UNAUTHORIZED` 응답 후 소켓 종료, `1`이면 첫 실패 직후 종료(§2.1 "필요 시 즉시 종료") |
| D9 | **인증 백엔드 오류** | 인증기가 예외를 던지면 `INTERNAL_ERROR`(실패 횟수에 합산하지 않음) |
| D10 | **`TRACE_ID` "16 Bytes / String"** | 두 형태 모두 허용: 길이가 16이면 임의의 바이트, 그 외 길이는 유효한 UTF-8 문자열이어야 함. `uuid.UUID`는 16바이트로 변환. 서버는 응답에 같은 `TRACE_ID`를 echo |
| D11 | **`CLIENT_ID`** | 인증되지 않은 참고 정보. 권한 판단에 쓰지 말 것 |
| D12 | **TLV 엄격성** | 잘림·길이 초과·잘못된 UTF-8·**표준 태그 중복**은 `BAD_REQUEST`. 알 수 없는 태그는 보존(순서 유지)하고 반복 허용. 단일 값 최대 길이는 `65,535 − 3 = 65,532`바이트(`Metadata Length`가 TLV 헤더까지 포함하므로) |
| D13 | **페이로드 한도** | "최대 16MB"를 `16 × 1024 × 1024`바이트 **포함**으로 해석(참조 코드의 `>` 비교). 정확히 16 MiB는 허용 (`test_payload_of_exactly_16_mib_is_accepted`). 서버는 더 낮은 `max_payload`를 설정할 수 있음 |
| D14 | **오류 페이로드** | 형식이 정의되어 있지 않아 JSON 관례를 사용: `{"error": {"code": 9, "name": "BUSY", "message": "...", "retry_after_ms": 50, "details": ...}}` (`Serializer`=JSON). 내부 예외 메시지는 클라이언트에 절대 싣지 않음 |
| D15 | **`BUSY` / `RATE_LIMITED`** | 같은 값(0x09). 서버: 연결당 토큰 버킷, 수용 상한(`max_in_flight`), 대기 페이로드 바이트 예산 초과 시 `BUSY` + `retry_after_ms`. 클라이언트: 힌트만큼 세션 전체 송신을 멈추고 지터를 더해 `busy_retries`회 재시도 |
| D16 | **서버 종료 중 요청** | 진행 중인 핸들러는 `grace` 동안 끝나기를 기다리고, 새 요청은 `BUSY("shutting down")`로 거절 |
| D17 | **TLS** | 헬퍼(`create_*_ssl_context`)는 TLS ≥ 1.3, 서버 인증서·호스트명 검증을 강제. TLS 없는 서버는 개발용으로 허용하되 루프백이 아닌 주소에 바인딩하면 경고 |
| D18 | **직렬화** | 알 수 없는 `Serializer`는 `BAD_REQUEST`(연결 유지; 프레임 경계는 안전하므로). Protobuf는 스키마 협상 없이 호출 측이 메시지 클래스를 지정 |
| D19 | **`PING`/`PONG`의 `Serializer` 바이트** | 의미가 없으므로 검증하지 않음 |

## 3. 명세보다 엄격하게 구현한 부분

- 헤더 검증은 §6 참조 프레이머와 **동일한 수락/거부 결과**를 내며(hypothesis 차분 테스트), 그 위에 Serializer·TLV·UTF-8·`TARGET_PATH` 검증을 더합니다.
- JSON은 RFC 8259 엄격 모드(`NaN`/`Infinity` 거부, 잘못된 UTF-8 거부, 재귀 폭탄은 `BAD_REQUEST`).
- 유효하지 않은 프레임이 반복되면(`max_bad_requests`) 연결을 종료합니다.

## 4. 명세에 없는 확장 (비규범)

토큰 버킷·바이트 예산·핸들러 동시성 제한, 클라이언트 송신 게이트, 이벤트 중복 억제, 읽기·쓰기·프레임 타임아웃과 쓰기 버퍼 상한,
서버 `max_connections`, 우아한 종료(grace), `lcp` CLI, 벤치마크 하니스. 모두 와이어 포맷을 바꾸지 않습니다.

## 5. 명세 개정 제안 (v1.4 후보)

1. §3.2의 "표 4.2 참조"를 "표 5.2 참조"로 수정.
2. "4바이트 정렬" 문구를 삭제하거나, 정렬을 원한다면 TLV·페이로드 패딩 규칙(그리고 길이 필드가 패딩을 포함하는지)을 정의.
3. 바이트 순서(빅엔디안)를 본문에 명시.
4. `PONG`의 Correlation ID, `EVT` 방향성과 `TARGET_PATH` 용도, 오류 페이로드 형식, `TRACE_ID` 형식(16바이트 vs 문자열 중 하나로)을 정의.
5. 헤더 위반 시 응답 여부를 §3.2와 §6 참조 코드에서 일치시킴 (E3).
6. 미정의 상태 코드의 수신 처리 규칙(거부/보존)을 명시.
